# Template variables have a closed source set

Workflow authors refer to runtime locations and task inputs with a single template-variable mechanism instead of making directory paths special-case tokens. A template variable appears as `${name}` in model-facing prose and parameterized gate inputs, and the control plane performs exact string substitution when a response or executable input is built.

Template variables have one closed source set. The only valid sources are the built-in `${workflowDir}` package directory, the built-in `${taskDir}` task artifact directory, and task inputs admitted by `wf start --var`; the latter use the start-variable name directly. Template resolution never reads arbitrary environment variables, runtime route facts, history, or project files, and never performs nested expansion, fallback matching, semantic interpretation, or shell evaluation.

Template variable names use one strict grammar. The reserved directory variables are exactly `workflowDir` and `taskDir`; all other references must use the existing start-input grammar, `^[a-z][a-z0-9_]*$`. The two reserved names cannot be overridden by task input, and the parser recognizes only complete `${name}` placeholders. It does not trim whitespace inside braces, match uppercase start-input spellings, use shell variable syntax, or provide an escape mechanism; a malformed reference is an operational error.

Substitution applies uniformly to stage guides, `file_exists` paths, command-gate command strings, human gate requests and evidence paths, `workflow_script` project arguments, and condition-producer commands and project arguments. The replacement is a single pass over complete string values, not recursive template parsing. An unresolved or malformed template variable is an operational error rather than an instruction containing a raw placeholder.

Validation is split by what each command can know. `wf validate` checks only template placeholder syntax, including reserved built-in names where possible, because it has no task inputs. `wf start` resolves every template referenced by the bound workflow against the start inputs and the built-in task and workflow directories; an unresolved variable is an operational error and the task is not created. Extra token-valid start inputs that are not referenced by a template may still be admitted and retained for audit.

This revision does not add a new post-substitution path-traversal hardening pass. Template replacement remains exact string substitution, and the existing project-relative path validation rules are unchanged. The narrow start-input token grammar is accepted as the current input boundary; hardening substituted path components beyond that grammar is deferred until a concrete requirement makes that trade-off necessary.

This general mechanism keeps route-condition variables and template variables distinct. A condition variable controls candidate-edge selection; a template variable supplies controlled runtime text to the active instruction or gate input. A start input may therefore be referenced as `${name}` without becoming a route fact or requiring any route condition to consume it.

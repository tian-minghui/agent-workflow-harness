# Condition variable resolution order and environment aliases

A transition condition sees only a logical condition-variable name. The control plane resolves that name through one fixed precedence:

1. if the active step declares a producer for the variable, rerun that producer and use its refreshed result;
2. otherwise read the existing runtime fact;
3. then the start input recorded by `wf start --var`;
4. then the strict `WF_<UPPER_SNAKE_NAME>` environment alias.

A variable that remains unresolved is an operational route-evaluation error and never makes a default edge available.

Active-step evidence outranks immutable start inputs because it is refreshed after the stage’s gates and optional human review. Existing runtime facts outrank start inputs and environment values because they record evidence already generated by the control plane. Start inputs express explicit caller intent and therefore outrank ambient environment values. Environment aliases are operator and test overrides, not ambient process variables: a name such as `technical_contract_required` may be overridden only through `WF_TECHNICAL_CONTRACT_REQUIRED` using the strict uppercase mapping.

An active-step producer is always rerun before selecting a route from that step. Later steps read the recorded fact and do not rerun a producer owned by an earlier step. The selected route record retains the logical condition variable, resolved value, and resolve source; the response still never exposes alternative transitions or future guides.

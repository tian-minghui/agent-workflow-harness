# Requirements — three-case harness validation

## 目标

Produce a repeatable session-control experiment for the deliverable and migration. The user-facing outcome is to understand whether executing the workflow through Agent Workflow Harness actually improves core professional judgments compared with the static skill baseline.

Produce a repeatable experiment that compares **Agent Workflow Harness** with a traditional “static skill containing step1/step2 instructions” control strategy. The experiment must show whether harness-driven execution gives:

1. more stable workflow progression,
2. more reliable gate enforcement,
3. equal or lower token/context cost than putting the whole process into one static skill prompt.

The record is namespaced under the dedicated project directory `docs/workflow-validation/`; this `docs/requirements.md` is the workflow-facing requirements entry for that dedicated experiment.

## Scope and constraints

- Compare harness against a static skill that exposes the complete stage sequence and asks the agent to self-advance.
- Keep the harness's core implementation unchanged. The experiment may add only isolated benchmark/record material under `docs/workflow-validation/` (or an equivalent dedicated experiment directory agreed there).
- Use actual CLI invocations in isolated project/control-plane sandboxes for harness observations.
- Use deterministic replay agents and scripted deviations for both harness and static-skill mode; the benchmark must not depend on a user sitting beside the machine.
- Preserve runnable commands, deterministic inputs, raw metrics, and interpretation in one place.
- Final delivery must include a conclusion that is honest about limitations. If harness does not improve a metric, report that as-is.

## Comparison model

Harness mode:

- Agent sees only the current work order returned by `awh start` / `awh next`.
- `next` has two possible onward signals: a runnable transition plan generated by the harness, or a blocked/repair order.
- Gates and stage identity are owned by the control plane.
- Historical evidence can be observed from the control plane without reading YAML in agent-facing protocol.

Static-skill mode:

- One immutable prompt containing `Step 1`, `Step 2`, `Step 3`, etc.
- The agent parses the full workflow, chooses the next step, and declares the step complete.
- Tests and gates are prose obligations in the prompt.
- Validate parity by using published harness and static-skill outputs only. Do not inspect future workflow instructions before the experiment; workflow internals are not part of the comparison contract.
- Workflow progression correctness is measured by accepted next-status and final `done`, plus whether the stage identity is physically captured rather than agent-declared.
- Gate enforcement correctness is measured by refusal to declare completion when the real artifact/gate is still invalid.
- Cost is interpreted as deterministic input-token/read-character exposure plus calls required to finish a case, not as wall-clock time.
- Repeated runs must be deterministic but fidelity to each agent role should be preserved.
- If raw CLI output is incomplete, rerun the focused case and preserve both the exception and a clean rerun; do not silently mix evidence bases.

## Validation cases

### Case A — progression stability against step drift

`docs/workflow-validation/case-a/`

A simulated agent, on a seeded replay stream, tries to advance from design to implementation before requirements exist. More generally, when the active stage is not ready, the harness must emit a blocked/repair work order or otherwise refuse a physical next transition until the current gate is satisfied. The static skill baseline allows the same agent replay to relabel/near-miss step completion and advance by prose.

Primary metrics:

- stage order adherence,
- number of illegal transitions / near-miss declarations,
- number of extra manual reconciliation calls,
- final completed steps and artifacts,
- raw work orders and static-skill agent decisions.

### Case B — gate enforcement reliability under failing test artifacts

`docs/workflow-validation/case-b/`

A deterministic site or helper target is furnished in three artifact states:

1. implementation valid, tests pass,
2. tests fail, implementation passes,
3. implementation passes only after a concrete test file/gate is repaired/created.

The harness must not complete the gate-passing stage until the real command exits zero. The static-skill baseline has a prose rule “must run `npm test` before complete”, but no physical control plane boundary.

Primary metrics:

- successful completions,
- blocked/retry counts,
- gate-check execution counts,
- number of false-complete declarations,
- stdout/stderr/error evidence,
- raw command-gate results.

### Case C — token/context cost comparison

`docs/workflow-validation/case-c/`

Compare total input content the agent must consume in three stages:

- harness work orders only (one current instruction per call),
- static skill with the complete multi-step process in the prompt,
- skill plus attempt bits that reproduce the harness input.

Use a deterministic token estimator and retain the exact inputs. The experiment must report both per-turn and cumulative input exposure, and separate work-order content from control-plane mechanical output.

Primary metrics:

- cumulative input characters,
- approximate input tokens,
- per-stage max context chunk,
- duplicate/future-stage exposure,
- number of control-plane calls,
- total workflow turn count as a structural proxy for accumulated history size.

## Acceptance criteria

1. `docs/workflow-validation/README.md` exists and explains the experiment, assumptions, and limitations.
2. Three case subdirectories exist and contain reproducible commands, inputs, raw results, and summaries.
3. A single, runnable benchmark script can regenerate results from a clean checkout/seeded environment.
4. The comparison includes at least two repetitions for each case or one recorded deterministic replay per case plus documented evidence; avoid single-run conclusions where the metric can apply in isolation.
5. Harness core code, gates, runtime, or tests are not modified for the experiment.
6. The experiment submits final tables, charts, conclusion, honest trade-offs, and the benchmark together in one clean commit.
7. All test/judge commands used during execution pass, unless a metric intentionally requires a failing gate.
8. The final report links back to this requirements document and states which claims are demonstrated, partially demonstrated, or not yet demonstrated.

## Out of scope

- Claims about branch behavior, speculative concurrency, ASGI runtime, token transfer, or single-turn self-selection; those need separate complete experiments.
- General quality judgments about other agents, engines, or repeated anticipating behavior.
- Making the harness look better by weakening the static-skill baseline.

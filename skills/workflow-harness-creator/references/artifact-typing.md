# Workflow Artifact Typing

## 原则

先判断阶段真实产生什么，再选择文件类型。

不要为了阶段整齐而强制统一成 Markdown 或 JSON。

## 产物类型

| 类型 | 适合形态 | 例子 |
|---|---|---|
| 状态 / 事务记录 | JSON / YAML / state | 工作项 ID、回执、锁定状态 |
| 机器结构化数据 | JSON / YAML | 任务包、路由计划、状态索引 |
| 人工阅读正文 | Markdown + frontmatter | 确认版 PRD、架构拆分、Spec |
| 条件产物 | 有则生成，无则状态 | 可选技术契约 |
| 可替换生成器 | 状态索引 + 动态引用 | 每个 Bot 由 specSkill 决定 |
| 外部引用 | 指针字段 | 代码文件、文档链接、artifact 引用 |

## Markdown 判定

仅当使用者确实需要阅读正文、执行人工审阅或后续交付时才生成 Markdown。

Markdown 模板通常只保留：

1. YAML frontmatter：机器校验字段
2. 正文的真实标题位或原模板引用
3. 需要人工填写的内容

不确定正文时，不要编造结构。

## JSON / YAML 判定

适合用 JSON 或 YAML 的场景：

- 状态记录
- 路由数据
- 任务包
- 清单
- 引用索引
- 自动 gate 直读数据

这类产物不需要为了可读性再额外生成说明书。

## 条件产物

如果阶段产物只在部分运行中出现：

- 用条件 producer 表达分支
- 不生成为空文档
- 在状态字段中写明 “没有该产物” 的原因
- 路由继续走真实终点，不制造占位文件

## 可替换生成器

如果阶段可能由外部 skill 或生成器执行：

- workflow 只保存驱动字段，例如 `specSkill`
- 不硬编码默认模板
- 不强制输出某个特定正文格式
- 用状态索引记录每次真实输出路径
- gate 校验输出的是结果文件，而不是 generator 名字本身

## 通用禁止项

- 为每个 step 预置同一个 stage 文件
- 填入 “范围 / 主体 / 结论 / 证据” 空话
- 把状态阶段硬改成 Markdown
- 把 JSON 产物再额外复制一份说明文档
- 在模板正文里编造业务内容

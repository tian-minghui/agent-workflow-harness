# Workflow Creation Clarification Protocol

## 原则

澄清不是拖慢创作，而是避免在证据不足时生成一个“看起来正确”的 workflow。

一个 workflow 只有在下面信息基本清楚后才开始写：

- 目标和结束条件
- 阶段边界
- 每阶段的真实产物
- 相邻阶段之间的转移条件
- 每阶段能被机器或人工证明的完成标准

如果这些信息存在硬阻塞，先向用户澄清；不要继续编造一个看似合理的默认方案。

## 必须澄清的硬阻塞

以下情况不能靠猜测继续：

| 缺失项 | 判断方式 | 应问的问题 |
|---|---|---|
| 目标 / 终态不清 | 无法用一句话写清目标或完成结果 | “这个 workflow 完成后，最终要产生什么？” |
| 阶段边界不清 | 不知道用户说的几个动作是否属于同一阶段 | “这几个动作是同一阶段，还是应拆成两个阶段？” |
| 产物属性不清 | 不知道每阶段是文档、状态、还是外部引用 | “这一步的真实产物是什么？” |
| 完成标准不清 | 得不出客观 gate | “这条完成后，能用什么事实证明？” |
| 路由条件不清 | 不知道下一个阶段是确定、有条件，还是需要人工选择 | “什么时候应该走 A，什么时候应该走 B？” |
| 人工确认边界不清 | 不知道是否需要用户审阅 | “这一步需要你确认，还是可以自动校验？” |
| 可替换生成器归属不清 | 不知道某阶段由哪个 skill / generator 生成 | “第 6 阶段由谁生成产物？” |
| 多个输入冲突 | 用户描述、既有 skill、系统文档结论不一致 | “这几份材料冲突，以哪份为准？” |

## 不需要澄清的情况

以下属于可默认项，不要为了它们反复打断用户：

- Workflow alias 未指定，可由目标推导
- 输出根目录未指定，可用 `.workflow-harness/<alias>/`
- gate script 存放位置未指定，可用 `scripts/`
- references、templates、scripts 的目录命名未指定，可按包结构推导
- 用户同意“你自己决定”且不影响业务语义
- 文件具体路径尚未确定，但产物形态和 gate 类型已经清楚

这类可以采用默认并说明原因，不需要每次都问。

## 澄清卡格式

一次最多 3 个问题。若超过 3 个，说明信息太分散，应先让用户确认主要目标或主线，再补充细节。

优先使用固定结构：
```
我需要澄清这些点：

1. <问题>
   - 你想走：
     A. <选项>
     B. <选项>
     C. 自定义
   - 建议：<differently-grounded reasoning>

2. <问题>
   - ...
```

问题必须：

- 直接指向缺失的判断点
- 提供可用选项
- 给出一个推荐答案
- 解释为什么这个问题会导致 workflow 结构变化
- 不要引入与当前阶段无关的新设计难题

## 示例

### 示例 1：阶段属性不清

```text
我需要澄清这些点：

1. 第 3 步“生成 Spec”是阶段本身，还是中间产物？
   - 你想走：
     A. 独立阶段
     B. 作为上一阶段的一部分
   - 建议：B
   - 原因：它已经有明确输入和完成标准，单独拆会重复 gate。

2. 第 6 步是否必须人工确认？
   - 你想走：
     A. 是
     B. 否
   - 建议：是
   - 原因：它影响方案定稿，不能只靠文件存在判断。
```

### 示例 2：路由条件不清

```text
我需要澄清这些点：

1. 第 4 步什么时候执行？
   - 你想走：
     A. 只要第 3 步完成就执行
     B. 只有第 3 步产生 X 时执行
     C. 由用户人工选择
   - 建议：B
   - 原因：“B” 才能形成真实 conditional producer，而不是猜测路由。
```

## 使用时机

在生成 `workflow.yaml` 之前，如果存在硬阻塞，必须暂停发一张澄清卡。
在收到用户回答之前，不要继续创建 workflow 包文件。

澄清不属于额外交互模式，而是创作协议的内部前置步骤。

## 收到回答后

1. 把答案补回阶段契约
2. 不再重复已澄清的问题
3. 若答案引入新的硬阻塞，最多再追问 1 轮
4. 再次越过 2 轮仍不清，说明原材料不适合当前精度，应改用更小的 workflow 或先补一份源材料
5. 确认最终 workflow 前不允许继续编造未确认字段

## 完成判定

澄清完成的标准：

- 目标和终态已能一句话说清
- 阶段边界可画成链路
- 每阶段真实产物清楚
- 每个产物能被 gate 或人工确认证明
- 每条路由都有明确条件或默认
- 不存在凭空假设的关键字段
